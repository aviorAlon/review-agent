# review-agent

一个面向 AI 代码审查的「多 Agent 编排 + 深度上下文」增强层。它把现有的审查器
（PR-Agent、Claude Code、任何 CLI agent）当作*可插拔后端*，让它们在同一份共享
的结构化上下文上并行运行，再用确定性的规则把各自的发现合并起来。

它不是 CodeRabbit 的竞品。它只做开源领域还缺的三件事，并且每一件都做成可以
单独验证的形态：

| 押注 | 代码位置 | 状态 |
|---|---|---|
| 深度上下文（不只看 diff） | `context/` | Python 走标准库 `ast`；其他语言是扩展点 |
| 多 Agent 扇出 + 基于规则的聚合 | `orchestrator/` | 可用、确定性、合并可审计 |
| 可插拔的 agent 后端 | `agents/` | LLM（LiteLLM）、外部 CLI、PR-Agent 基线、fake |

## 五分钟上手，不需要 API key

```bash
pip install -e .
review-agent demo --repo . --diff-file tests/fixtures/sample.diff   # 跑一遍流水线，用确定性后端
review-agent bench                                                  # 跑基准，零成本的启发式审查器
```

第一条命令端到端地演示一次审查；第二条把一个正则审查器放到真值集上打分，
打印召回、精确率和置信区间。所有东西都不会离开你的机器。

## 接上模型

```bash
cp .review-agent.example.yaml .review-agent.yaml     # 选一个模型 / 代理，设置它指定的环境变量
review-agent review --base main                      # 本地运行，打印发现
review-agent review --base main --json               # 机器可读
review-agent review --base main --post gitlab --fail-on-critical   # 在 CI 里：行内评论，并卡住 MR
```

把它放进 Jenkins / GitHub Actions / GitLab CI 就是一条 shell 步骤。这*就是*
CI 集成；没有插件需要安装。

## 什么会被发送给模型

每次审查模型收到的是：

- 变更文件的 diff（每个 hunk 内的新增、删除、未变行，带行号），在 `exclude:`
  规则和 `limits:` 生效之后；
- 上下文引擎开启时（默认开启）：每个被改动的函数的签名、它调用的名字、
  **仓库中其他位置每个调用点周围带行号的源码**，以及 **它调用的项目内函数的
  函数体** —— 这些是 diff 从未触碰的未变代码；
- 配置里的自由文本 `rules:`，原样发送。

除此之外什么都没有：没有文件列表、没有 git 历史、没有环境信息。`--no-context`
只发送 diff。所有内容都发往配置里 `api_base` 指定的地址 —— 某个厂商，或者你
自己的代理 —— 不会发到别处；本工具没有遥测。在把它指向一个你不希望把调用方
代码交给第三方的仓库之前，请记住这一段。

## 校验器：标记，而不是删除

第二阶段的校验器会对照 diff 重读每一条发现。默认情况下（`verifier_mode: flag`），
否定的裁决会把该条发现降级为 INFO，并附上理由；它仍然会到达作者手里，并且
永远不会阻断 CI。`drop` 则直接移除。之所以默认是 flag，是因为在真实代码上
校验器曾经删掉过一条真实的发现（见「结果」）；而基准测试始终测的是 drop 模式，
因为那正是它要回答的问题。

## 成本护栏

`limits:` 限制文件数、hunk 数、hunk 大小和总提示词大小；`exclude:` 跳过
vendored、生成的、lock 和压缩文件。被裁掉的内容都会列在发布摘要的「Not reviewed」
之下 —— 一次悄悄只看了半个 PR 的审查，比一次明说自己没看完的审查更糟。

## 发布到 MR / PR

`--post auto` 从环境变量里嗅探托管平台；`--post gitlab|github` 强制指定。

| 平台 | 读取的环境变量 | 发布内容 |
|---|---|---|
| GitLab | `CI_PROJECT_ID`、`CI_MERGE_REQUEST_IID`、`CI_SERVER_URL`、**`GITLAB_TOKEN`** | 每条行内发现一个 Discussion + 一条 Note 作为摘要 |
| GitHub | `GITHUB_REPOSITORY`、`GITHUB_REF`、`GITHUB_API_URL`、**`GITHUB_TOKEN`** | 一个 PR Review 承载全部行内评论，摘要在其正文中 |

```yaml
# .gitlab-ci.yml
review:
  script:
    - pip install -e .
    - review-agent review --base $CI_MERGE_REQUEST_DIFF_BASE_SHA --post auto --fail-on-critical
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

两个平台都拒绝在 diff 之外的行上做行内评论。发现会先按 hunk 范围划分：范围内
的走行内，其余的（hunk 之间的行、不在 diff 里的文件、外部 CLI agent 给出的
`UNKNOWN` 兜底）落到摘要 Note 里，而不是被丢掉。在 GitLab 上，被 API 拒绝的
行内评论同样会降级到摘要里。

`GITLAB_TOKEN` 必须是带 `api` 权限的项目/个人访问令牌；`CI_JOB_TOKEN` 不能
创建 discussion。

## 一次审查如何运行

```
diff ──> parse_diff ──> ContextEngine ──> Orchestrator ──> aggregate ──> findings
             │              │                  │               │
          Hunk[]     ContextBundle       AgentResult[]    merge/rank/cap
                     (hunks + symbols   (one per backend,  (rule-based,
                      + repo rules)      errors kept)       no LLM)
```

- 上下文**只构建一次**并共享；每个 agent 看到的输入完全相同。
- 超时或崩溃的后端会返回一个设置了 `error` 的 `AgentResult`。它永远不会取消
  其他 agent，也永远不会无声消失。
- 重复 = 同一文件、同一类别、相距不超过 `line_window` 行。置信度更高的发现
  留下；被合并掉的那条的 agent id 记录在 `merged_from` 里，这样合并事后可以
  审计，而不是靠猜。

## 消融开关（用于验证研究）

| 臂 | 命令 |
|---|---|
| A：基线，仅 diff | yaml 里一个 `llm` agent，`--no-context` |
| B：+ 上下文 | 同一个 agent，去掉 `--no-context` |
| C：+ 编排，仅 diff | 完整阵容，`--no-context` |
| D：全开 | 完整阵容 |

每条发现都带着 `source_agent` 和 `merged_from`，因此可以隐藏来源做盲标，
之后再重新归因。

## 添加一个后端

继承 `agents.base.TimedAgent`，实现 `_run(context) -> list[Finding]`，并在
`config.build_agents` 里注册一个 `type`。编排器只看得到 `ReviewAgent.review()`。

要包一个外部 CLI agent 甚至不需要写代码：在 yaml 里加一条 `type: cli`。它会
从 stdin 收到 diff + 结构化上下文。优先结构化 JSON；自由文本也能容忍，会被
包成一条低置信度的发现而不是丢弃。

## 给上下文引擎添加一种语言

为该语言实现 `find_enclosing_symbol(source, line)` 和
`find_callers(repo_root, name, exclude_file)`（tree-sitter 是显而易见的底层），
然后在 `context/engine.py` 里按扩展名分发。Agent 只会看到 `SymbolRef`，所以
下游什么都不用改。

## 基准测试（测量本身，而不只是流水线）

```bash
review-agent bench                                   # 零成本启发式阵容，臂 A-D
review-agent bench --config .review-agent.yaml       # 真实阵容（需要 LLM key）
review-agent bench --arms A,D --json
review-agent bench --export-labels labels.jsonl      # + labels.jsonl.key.json
```

`bench/cases.py` 里有 20 个微型的「改前/改后」仓库：14 个各注入了一个缺陷
（6 安全、6 逻辑、2 性能），6 个是干净的改动。Diff 由两个状态生成，从不手写。
每条真值都有一个 `snippet`，加载器会拿它核对所声称的行号，这样数据集不可能
偏离自己的答案。

按真值打分，容差 3 行：*strict* = 同文件 + 同类别；*loose* = 同文件、任意类别。
精确率使用 loose 匹配。之所以有干净用例，是为了让精确率有意义：在干净用例
上的每一条发现都是误报。区间是按用例做的百分位 bootstrap。

### 目前的结果

启发式 agent（零成本）：召回 0.86 [0.62, 1.00]，精确率 1.00，干净用例误报 0/6，
各臂完全相同，因为它从不读上下文。漏掉的是 `logic-none-deref` 和
`logic-stale-closure` —— 正则看不见的语义。把它理解成它自身的上界：规则和
用例是同一个人写的。

#### 第 1 轮（已作废）：测试台撒了谎

`bench-results/2026-10-13-gpt-5.5-proxy.json`。臂 A 当时是 `agents[:1]`，
悄悄把*安全专家*当成了基线。它的 strict 召回 0.43，对比专家组的 1.00 ——
这个数字量的是阵容构成，不是编排。类别当时也是绑在 agent 上而不是按条发现
分类的，所以去重比较的是 agent 身份。两者都已修复；这一轮留着当作错误的记录。

#### 第 2 轮：通才基线 vs 专家组，同一模型

`gpt-5.5` 经代理调用，角色显式声明，类别由模型分类。
`bench-results/2026-10-13-gpt-5.5-proxy-v2-roles.json`。

| 臂 | 阵容 | 召回 (strict) | 精确率 | 干净误报 | 发现数 | 重复 | agent 秒 |
|---|---|---|---|---|---|---|---|
| A | 通才，无上下文 | 0.93 [0.77, 1.00] | 1.00 | 0/6 | 13 | 0 | 80 |
| B | 通才，+ 上下文 | 1.00 | 1.00 | 0/6 | 15 | 1 | 77 |
| C | 3 专家，无上下文 | 0.93 | 0.94 | 1/6 | 17 | 3 | 182 |
| D | 3 专家，+ 上下文 | 1.00 | 1.00 | 0/6 | 17 | 3 | 170 |

通才在命中上的类别准确率：13/13。行号准确率：A 11/13 精确，D 12/17 精确
（+4 差一行）。200 次调用，零错误。

- **「多 Agent 更强」不成立。** 一次通才调用在召回上追平三个专家，发现更少、
  重复更少、没有干净用例误报，并且只用 45% 的 agent 时间。按类别拆分的专家
  在这个数据集上只买来了噪声和成本，别的什么都没有。PRD 里的并行专家架构，
  就这份证据来看，对召回而言是错误的拆分方式。
- **上下文在两组对照里翻转了同一个用例。** A→B 和 C→D 各自恰好多拿到
  `logic-none-deref`。同一条真值上的两次独立观察，单轮，模型默认温度：
  有提示性，不是证据。重复跑和跨文件用例才能把它变成证据。
- **模型分类的类别修好的是测量，不是重复。** 专家们仍然会给同一行打上不同
  但都站得住的标签（TOCTOU：安全*和*逻辑），所以基于规则的合并仍然什么都
  折不掉。重复是专家阵容的属性。通才几乎不产生重复。
- **于是真正的问题变了。** 不再是「专家 + 校验器（E）能否胜过专家（D）」，
  而是「通才 + 上下文 + 校验器（F）能否胜过通才 + 上下文（B）」。臂 F 就是
  为此存在的；E 保留下来，用来看校验器能否清掉专家阵容的重复。
- 仍然成立：精确率 1.00 受限于过于干净的用例；成本只有时间；N 是 20 且自己
  写的。

#### 第 3 轮：校验器臂，B/D 在同一轮里重采样

`bench-results/2026-10-13-gpt-5.5-proxy-v3-verifier.json`。同样的阵容加一个
`gpt-5.5` 校验器。臂 E = 专家 + 校验器，F = 通才 + 校验器（产品形态的那一臂）。
200 次调用，零错误。

| 臂 | 阵容 | 召回 (strict) | 精确率 | 干净误报 | 发现数 | 重复 | 删除 tp/fp | agent 秒 |
|---|---|---|---|---|---|---|---|---|
| B | 通才，+ 上下文 | 1.00 | 1.00 | 0/6 | 14 | 0 | - | 75 |
| D | 3 专家，+ 上下文 | 0.93 | 0.94 | 1/6 | 17 | 2 | - | 186 |
| E | 专家 + 校验器 | 0.93 | 1.00 | 0/6 | 15 | 1 | 0/0 | 189 |
| F | 通才 + 校验器 | 1.00 | 1.00 | 0/6 | 14 | 0 | 0/0 | 109 |

- **校验器在 40 次用例运行里什么都没删。** E 与 D 的差距是专家的采样方差
  （独立样本），不是校验器的动作。直接在 `logic-toctou` 上探测：它跑了，返回
  `keep` 并给出正确、实质的理由，没有杀掉任何真阳性。它之所以无所作为，是
  因为各臂没有递给它任何可删的假阳性。端到端的臂不是测精确率阶段的正确仪器；
  见下面的候选池回放。
- **通才 vs 专家在两轮里都成立。** B：两轮都是 1.00 / 1.00（15→14 条发现，
  1→0 重复）。D：1.00→0.93（这次丢了 `logic-toctou`），3→2 重复，干净用例
  误报又出现了。各两个样本，但通才既更便宜也更稳。
- **专家的干净用例误报可复现，而且有一张脸。** 两次都是*性能*专家，两次都在
  `clean-extract-helper` 上：对抽取出来的 `line_total(i)` 辅助函数报「每次
  迭代的函数调用开销」，严重度 INFO。一个专家在自己车道里没活干时仍然会
  产出点什么。通才在四个样本里从没这样过。
- **标签一致时去重确实会合并。** TOCTOU 探测里两个专家都把它分类成 `security`，
  于是规则把它们折在一起（`confidence 1.00` = 一致加成）。第 2 轮的「合并为零」
  部分是逐轮变化的标签分歧，不是死代码路径。
- **上下文，在唯一承载信号的用例上重测。** `logic-none-deref` 在第 2、3 轮的
  每一个带上下文的臂（B×2、D×2）里都被找到，而第 2 轮的两个无上下文臂（A、C）
  都没找到。仍是一条真值；现在是六次一致的观察。

#### 第 4 轮：提示词里加入 hunk 的上下文行

`bench-results/2026-10-13-gpt-5.5-proxy-v4-context-lines.json`。在这一轮之前，
提示词只展示新增/删除行；hunk 内部的未变行是看不见的，所以审查器看不到改成
`range(len(prices) + 1)` 之下的 `s += prices[i]`。现在目标侧按行序渲染
（`+` 新增，`' '` 未变，两侧都有行号）。

| 轮 | 臂 | 召回 (strict) | 精确率 | 发现数 | 重复 | 精确行号 TP | agent 秒 |
|---|---|---|---|---|---|---|---|
| 2（无上下文行） | B | 1.00 | 1.00 | 15 | 1 | 11/13 | 77 |
| 3（无上下文行） | B | 1.00 | 1.00 | 14 | 0 | 12/15 | 75 |
| **4（有上下文行）** | B | 0.93 | 1.00 | 13 | 0 | **12/13** | 72 |
| 3（无上下文行） | F | 1.00 | 1.00 | 14 | 0 | - | 109 |
| **4（有上下文行）** | F | 0.93 | 1.00 | 13 | 0 | 11/13 | 92 |

- 第 4 轮两个臂都丢了 `logic-none-deref`。当时这被解读为上下文信号减弱。
  其实不是：见第 5 轮。

#### 第 5 轮：删除行锚定到原来的位置

第 4 轮的渲染把删除行列在所有目标侧行*之后*，于是一条被删掉的
`if user is None:` 出现在它原本保护的 `return user.email` 下面，读起来像不可达
代码。通才正确地读了一幅错误的图，于是不再标记它。同样渲染下的校验器候选池
回放让这一点无可辩驳：丢了 7 条真值，其中 6 条是这个用例，每条理由都是「被删
的检查在 return 之后，所以不可达」。现在每条删除行都带着它原本跟随的目标行，
并渲染在那里。`bench-results/2026-10-13-gpt-5.5-proxy-v5-anchored.json`。

| 轮 | 臂 | 召回 (strict) | 精确率 | 发现数 | 重复 | 精确行号 TP | agent 秒 | token |
|---|---|---|---|---|---|---|---|---|
| 5（上下文，锚定） | B | **1.00** | 1.00 | 15 | 1 | **14/15** | 96 | 10,715 |
| 5（上下文，锚定） | F | **1.00** | 1.00 | 15 | 1 | 14/15 | 99 | 17,657 |

- `none-deref` 在两个臂里都回来了：带上下文在它上面的战绩是 8/9，唯一的
  漏报有明确的原因。仍是一条真值；仍不是证明。
- 迄今最好的行号准确率（14/15 精确）—— 上下文行一旦不再在顺序上撒谎，就
  做到了它们该做的事。
- 第一批 token 数字：通才每个用例约 540 token；校验器增加约 65% token 和
  每用例约 3 秒，并且在这个数据集上什么都删不掉，因为没有东西可删。在输入
  有噪声之前，这就是 F 相对 B 的诚实代价。
- 校验器候选池回放，三种渲染，同样的 112 组 / 122 候选
  （`bench-results/2026-10-13-verifier-pool-eval*.txt`）：

  | 渲染 | 删除的 FP | 去掉的重复 | 丢失的真值 | 错误 |
  |---|---|---|---|---|
  | 仅新增/删除 | 2/2 | 3 | 1（「没有展示循环体」） | 0 |
  | + 上下文，删除行在末尾 | 2/2 | 3 | **7**（保护「不可达」） | 0 |
  | + 上下文，删除行锚定 | 1/2 | 3 | **0** | 0 |

  一旦 diff 被诚实地渲染，真值零丢失。这次它留下的那一条 FP，正是它之前两次
  都删掉的性能小毛病 —— 2 条是方差的样本，不是比率。失败开放（fail-open）
  全程成立：从没有东西因为出错被删，只有（有时被误导的）判断。

`review-agent bench-verifier --pool labels.jsonl --config ...` 把一个带标签的
候选池（真实的第一阶段输出，带真值 `is_tp`）回放过校验器。**按真值**打分：
只有当覆盖它的所有候选都被删时，真值才算丢失；一个被删的 TP 若其真值仍被
覆盖，就是去重起了作用。分组按 (pool, arm, case) 键控，这样不同轮的候选永远
不会碰面 —— 第一版把两轮合并进一组，校验器正确地删掉了同一条见了两次的
发现，而打分器把它报成了 30% 的真阳性误杀率。

在第 2 + 3 轮候选池上的结果（`bench-results/2026-10-13-verifier-pool-eval.txt`），
用第 4 轮之前的提示词（无上下文行）回放：

| 组 | 候选 | 删除的 FP | 去掉的重复 TP | 丢失的真值 | 精确率 |
|---|---|---|---|---|---|
| 112 | 122（120 tp / 2 fp） | **2 / 2** | 3 | **1 / 110（1%）** | 0.98 → 1.00 |

- 两条假阳性（性能专家的「辅助函数调用开销」小毛病）都被以「推测性的微优化，
  没有证据表明该路径是热点」删掉 —— 理由正确。
- 唯一丢失的真值是 `logic-off-by-one`：*「没有展示循环体，所以看不到 i 被用来
  索引 prices 的证据。」* 那是第 4 轮修掉的上下文行缺口，不是判断错误。
  带上下文行重新回放就是对它的检验。
- 去重去掉了大约 7 对同轮重复中的 3 对；它留下的几对是同一行上两个不同的
  真实观察（注入 + None 处理），这是站得住的决定。
- 只存在 2 条假阳性可删。2/2 是一个方向，不是比率。校验器的基准需要更吵的
  输入 —— 真实的干净 PR —— 删除率才有意义。

`--export-labels` 写出一个打乱顺序的 JSONL，只展示文件/行号/严重度/消息/推理，
外加一个把每个 `label_id` 映射回臂、来源 agent 和真值命中的 key 文件。先盲标，
再归因。

### 跨文件套件：对上下文的第一次真正测试

`--suite crossfile`：12 个用例，每个都是只改一个文件、单看无害的 diff。它是不是
缺陷由一个未改动的第二个文件决定 —— 一个把 `request.args` 递给它的调用方、
一个名叫 `safe_join` 却不做清洗的被调函数、一处调用点上的合规注释。六个缺陷，
每个都配一个干净的镜像：同一份 diff，另一个文件让它变得安全。只看 diff 的
审查器分不清这些配对，因此上下文应当在一半上提高召回、在另一半上降低误报。

为此上下文引擎从「调用方：file:line」加深为每个调用点周围带行号的代码，再加上
项目内被调函数的函数体；外围符号查找现在也先尝试被改动的行（带三行前导上下文时，
hunk 的起点通常落在函数上方）。

通才，两轮（`bench-results/2026-10-14-crossfile-A-vs-B*.json`）：

| 臂 | 轮 | 召回 (strict) | 精确率 | 干净镜像上的 FP | 发现数 | token |
|---|---|---|---|---|---|---|
| A，无上下文 | 1 | 0.50 | 0.50 | 4 / 6 | 8 | 7,832 |
| A，无上下文 | 2 | 0.50 | 0.50 | 4 / 6 | 8 | |
| B，+ 上下文 | 1 | **0.83** | **0.71** | **2 / 6** | 7 | 9,094 |
| B，+ 上下文 | 2 | **1.00** | **0.75** | **2 / 6** | 8 | |

按用例看，两轮除一个外在所有结果上一致：

| 用例 | A | B | 上下文展示了什么 |
|---|---|---|---|
| fake-safe-join | 漏, 漏 | **中, 中** | 被调函数体：`safe_join` 只是个普通的 `os.path.join` |
| caller-passes-none | 漏, 漏 | **中, 中** | 调用方：`db.get(...)  # None once deleted` |
| callee-returns-none | 漏, 漏 | **中, 中** | 被调函数 docstring：失败时返回 None |
| caller-threads | 中, 中 | 漏, 中 | 泛泛的「global += 不是线程安全的」；唯一不稳定的结果 |
| untrusted-name, staff-invoice | 中, 中 | 中, 中 | 仅凭模式就标出 |
| allowlisted-name, single-thread, staff-moderates | 误报, 误报 | **干净, 干净** | 调用方做了校验 / 是串行的 / 说明由员工审核 |
| caller-guards-none, callee-raises | 误报或干净 | 误报, 误报 | 看到了保护和会抛异常的被调函数，仍然标 None 解引用 |

- 缺陷：无上下文 6/12，有上下文 11/12。镜像上的误报：无上下文 8/12，
  有上下文 4/12。同一模型，+16% token。
- 上下文压不住的两条误报两轮都一样：模型即便看到了阻止它的代码，仍坚持一条
  推测性的「可能为 None」。这正是校验器存在的意义所要做的判断；在这个套件上
  还没有针对它们跑过。
- 警告，再锐化一下：用例的作者就是上下文引擎的作者，所以这是它自身的上界；
  N 是 6+6。两轮在 24 个结果里有 23 个一致，说明效应在这个套件上是稳定的，
  不说明它能迁移到真实代码。下面的 httpx 运行才是那个测试。

### 真实仓库：encode/httpx

`review-agent mine --repo httpx --mode recent` 取最近 15 个触及 Python 的非合并
提交（10-400 行 diff，≤6 个文件）作为噪声压力用例：在一个成熟仓库里，已合并
的改动被假设为干净，所以每条发现都是候选误报。这个假设在下面被检验；它没能
完整地活下来。

通才，带上下文（`bench-results/2026-10-14-httpx-recent-B-F.json`）：

| 臂 | 发现数 / 15 提交 | 每提交 | 删除 | token |
|---|---|---|---|---|
| B 通才 | 3 | 0.20 | - | 66,109 |
| F 通才 + 校验器 | 5 | 0.33 | **0** | 88,166 |

它说了什么（全部）：

- `_urls.py`：query 编码现在不再转义 `;` —— 对把 `;` 当分隔符的解析器来说
  是参数注入。该提交有意按 WHATWG 修订了安全字符集；行为变化是真的，算不算
  缺陷由维护者说了算。
- `_urlparse.py`：凭据里裸的 `%` 不再被转义。同一提交家族，同一个字符：
  真实的改动，可以说是有意的。
- `tests/test_api.py`：既然导入 httpx 不再导入 httpcore，`del sys.modules['httpcore']`
  现在是无条件的 —— 该测试单独运行时会 `KeyError`。可信、具体、可核实。
- `_models.py`（一个纯「移动函数」的提交）：Link 头解析用 `param.split("=")`
  而不限制分割次数，所以一个含 `=` 的带引号的值会把该参数及其后面的全部丢掉。
  一个被搬运带过来的既有 bug —— 正是「假设干净」看不见的那种。

所以在真实、成熟的代码上通才很安静（每 3-5 个提交一条发现），而它提出的东西
实质到「误报」需要人来裁定。校验器看到这五条候选，五条全留；对其中至少两条
来说这是正确的决定。通才在真实代码上的噪声压力很低 —— 专家组的运行（下文）
才是预期有噪声的地方。

`--export-labels` 写出了盲标用的候选池（`httpx-recent-BF-labels.jsonl`）；在有人
标它之前，上面的每提交计数是仅有的诚实数字。

三个专家在同样的 15 个提交上
（`bench-results/2026-10-14-httpx-recent-D-E.json`）：

| 臂 | 发现数 | 每提交 | 按专家 | 删除 | token |
|---|---|---|---|---|---|
| D 专家 | 10 | 0.67 | 性能 3 · 逻辑 5 · 安全 2 | - | 161,195 |
| E 专家 + 校验器 | 6 | 0.40 | 性能 2 · 逻辑 3 · 安全 1 | **0** | 175,202 |

专家组用 2.4× 的 token 产出了通才 3.3× 的发现。多出来的恰恰是合成套件预言
的东西：性能专家的「certifi 被无条件导入」和「每次请求都重新导入 httpcore」
（Python 缓存导入；这些是 INFO 级的小毛病），加上同一条 `%`-in-userinfo 发现
在三个不同行上的近似复述，而基于规则的合并折不掉它们。真正新的贡献只有一条：
`_decoders.py`，在那个专门处理空 zstd 响应的提交里，空 chunk 被当成 zstd 数据
处理 —— 具体、切题，值得维护者花一分钟。

然后把两轮的每一条第一阶段发现都回放过校验器
（`bench-results/2026-10-14-httpx-recent-verifier-replay.txt`）：24 个候选，
14 组，0 错误，**删了 2 条** —— 都是「每次请求的局部导入」，理由是*「对 Python
缓存导入机制的推测性微性能担忧」*。正确。但实况的 E 运行留下了同样这两条，
而回放又留下了专家 D 在同样行上对同一小毛病的另一种措辞。在真实代码上，校验器
对那一类明显噪声大约一半时间会删，并且在轮次之间摇摆；实质内容一条没删。
（那次回放里精确率显示 0.00，只是因为这些用例按构造不含真值。）

轨道 2 的结论：在成熟的真实代码上，噪声来自专家而不是通才；校验器安全但对
噪声无力；「合并了就是干净的」错得足够频繁，以至于这里的真值必须是带标签的
候选池，而不是一个假设。

### 真实 bug：从 httpx 用 SZZ 挖出的配对

`review-agent mine --mode fixes`：提交信息说修了什么的提交（排除工具/类型/文档），
取每个修复 REMOVED 的行，在修复的父提交上 `git blame`，写下那些行的提交成为
用例；被 blame 到的原始行号就是真值。15 个引入 bug 的提交，27 条真值，没有一条
出自这里的任何人之手。`bench-results/2026-10-14-httpx-fixes-B-F.json`。

| 臂 | 召回 (loose) | 精确率 | 发现数 | 被校验器杀掉的真值 | token / 用例 |
|---|---|---|---|---|---|
| B 通才 + 上下文 | **0.22** [0.07, 0.45] | 0.35 | 17 | - | 8,393 |
| F + 校验器 | 0.11 [0.00, 0.27] | 0.20 | 15 | **1** | 13,822 |

通才命中的六条真值是在引入它们的那个提交上抓到的真实 bug：IPv6 和 CIDR 的
`NO_PROXY` 条目被错误解析（正是后来的修复，在那条链的两个提交里）、一个会拒绝
合法文件类对象的二进制模式检查、`Headers.update` 丢掉重复值、根相对 URL 在没有
基础 URL 时丢掉斜杠、异步流里的一次同步读。具体，在正确的行上，在 bug 发布之前。

为什么这个数字既太低又太高：

- **SZZ 真值是行级且狭窄的。** 三个零发现的漏报里，有真值落在*测试夹具的字节串*
  上（`test_cookies.py:60`，一个 `Set-Cookie` 字面量）和一行
  `if hasattr(self._stream, "read"):` 上 —— 那是 blame 落下的地方，不是审查器
  能看出缺陷的地方。对这些的召回是一个下界。
- **若干「误报」是同一个 bug 在另一行。** 在 `chunk_size` 提交上，其后来的修复是
  「iter_text 加了一个空 chunk」，通才标的是「`iter_bytes()` 对缓存的空响应抛
  异常」—— 同一缺陷家族，修复没碰的行。在 `Map HTTPCore exceptions` 提交上它
  标出只有最初的 `transport.request` 被包了，迭代期间的异常会未经映射地逃逸：
  一个很久以后才修的真实 httpx 问题。在 `stream_lines` 上它标出跨 chunk 的裸
  `\r` 分割 —— 修复是「与标准库行分割保持一致」。对 SZZ 真值的精确率是一个上界。
- **校验器杀掉了一条真的。** F 丢了 IPv6 `NO_PROXY` 的发现（`fix-682cad39eb`），
  这是它在合成回放 0/110 之后在真实代码上的第一次真值丢失。F 更低的召回主要是
  一次独立的第一阶段采样（15 对 17 条发现）加上这次误杀；校验器现在在真实代码上
  赢得了一个硬性的「标记，别删」问题。
- 真实 bug 提交很大：一次通才调用每用例 8.4k token，带校验器 13.8k。

轨道 3 的结论：通才在引入时大约能找到五分之一被 blame 到的缺陷，而且找到的
是真的；真值在两个方向上都有噪声，所以下一步不是挖更多，而是让人过一遍这个
候选池，标出哪些「误报」其实是换了个名字的 bug。在那之前，0.22 是诚实的数字，
区间是 [0.07, 0.45]。

### 三个仓库

同样的两套配方 —— 假设干净的最近提交、SZZ 挖出的 bug 配对 —— 在 `pallets/click`
和 `psf/requests` 上（各 10 个用例，臂 B 和 F，
`bench-results/2026-10-14-{click,requests}-*`），与 httpx 并列：

| 仓库 | bug 配对：真值 | B loose 召回 | B 发现数 | 最近提交：发现 / 提交 | 校验器删除（任一臂） | token / bug 用例 |
|---|---|---|---|---|---|---|
| httpx | 27 | 0.22 | 17 | 0.20 | 0 | 8.4k |
| requests | 18 | 0.11 | 9 | 0.00 | 0 | 3.3k |
| click | 21 | 0.00（F：0.14） | 14 | 0.50 | 0 | 7.3k |

逐条发现的视角给这张表补充的东西：

- 在 click 上通才的「漏报」包括*「Windows 启动路径在 shell=False 下尝试执行
  shell 内建的 `start`」*、*「Popen 在 shell=True 时传了列表」*和
  *「_tempfilepager 丢掉了 pager 命令参数」*，都在那条后来的修复标题为
  *「Fixes windows specific error」*的提交链上 —— 就是那个 bug，在修复没碰的行上。
  与 httpx 同样的模式：行级 SZZ 真值是召回的下界。
- 在 requests 上两条命中是引入提交上的 `self.error` / `self._error` 不匹配，
  以及流式解码里缺失编码的处理。「误报」里有：分块请求绕过配置的超时、失败时
  连接池连接未归还、gzip 错误被吞掉。
- click 最近提交上的发现（*临时 pager 文件以文本模式打开却不用算出来的编码*、
  *`_is_expected_type` 比较的是 type 参数的类型*）属于只有人工标签才能裁定的那种。
- **校验器在三个仓库的任何一次实况运行里都没删过任何东西。** 观察到的所有
  删除都发生在回放里。flag 模式作为默认是正确的选择；它在真实代码上的实况
  价值未被证明，需要带标签的噪声才能测量。

跨三个仓库，诚实的总结是：通才在引入 bug 的提交上能抓到狭义历史 bug 的十分之一
到五分之一，它说的话具体到值得维护者花一分钟，而这里的每个数字都受限于尚未有人
标注的真值。候选池已导出；`label-import` 在等着。

## 在你自己的代码上测量一个配置

```bash
review-agent mine --repo . --mode fixes  --n 15 --out bugs.json    # 引入了后来被修复的 bug 的提交；真值来自 git blame
review-agent mine --repo . --mode recent --n 15 --out clean.json   # 最近合并的提交，假设干净

```

## FAQ

**为什么是一个通才而不是专家组？** 同一模型下，专家组在召回上追平通才，却多了
重复、一条在无害重构上可复现的性能小毛病，以及 2.4× 的 token —— 在合成数据和
真实提交上都是如此。如果在*你的*代码上的基准说了相反的话，就把它们打开；
`compare` 就是用来弄清楚这一点的。

**为什么校验器不删除？** 它在真实代码上删过一次真实的发现。在 `flag` 模式下，
一次错误裁决的代价是一个 INFO 标记；在 `drop` 模式下，代价是那条发现。

**我的语言显示「diff-only context」。** Python 什么都不用装；JS/TS、Go 和 Java
需要 `pip install "review-agent[languages]"`；其他语言只从 diff 审查，摘要里会
说明。添加一种语言只需两个函数：`docs/BACKENDS.md`。

**能用我自己的 agent 吗？** 能：`type: cli`，任意命令，契约在 stdin 上。
Claude Code 已验证。PR-Agent 作为后端是实验性的。

**重跑之后我的 MR 评论去哪了？** 还在；重跑会跳过已发布的发现（指纹），并更新
那唯一的一条摘要 note。

**要花多少钱？** 在真实仓库上通才每个提交大约 4-9k token，带校验器 +65%；
`--json` 和 `--audit-dir` 会报告每次运行的精确数字。
